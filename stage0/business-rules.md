# 业务校验规则

本文件对应 Stage 0 已确认的 **5B（Schema 保持多选，业务校验拦截）**、**E2（关键字段证据）**、**3A（全局代理人区块）** 和 **6A（错误分级）**。

业务校验器是独立于 JSON Schema 的一层；**不修改** 根目录的 `loan_complaint.schema.json`。

## 1. 状态定义

| 状态 | 条件 |
| --- | --- |
| `ok` | 结构校验通过 + 业务校验通过 |
| `needs_review` | 结构校验通过，但存在业务警告/冲突/缺失关键证据 |
| `error` | 结构校验失败、模型调用失败、无原告/被告、主体记录全空、无法生成可用结果 |

`status=ok` 不能只代表“Schema 通过”；必须同时通过本文件的业务规则。

## 2. 主体规则

### 2.1 当事人存在性

- 至少一个 `原告` 记录；
- 至少一个 `被告` 记录；
- `第三人` 可以为 `null`；
- 任何当事人记录不能所有 `data` 叶子全为 `null`；
- 违反以上任一条 → `error`，返回 `NO_PARTIES` 或 `EMPTY_PARTY`。

### 2.2 主体索引

- 所有当事人必须有内部 `subjectId`（`P1`、`P2`…）；
- `subjectId` 只在 review 和内部上下文出现，不进入业务 `data`；
- 每个 `subjectId` 至少有 1 条 evidence；
- 同一姓名/称谓出现多次时，必须通过角色、地址、证件号或上下文区分，不能默认合并。

## 3. 代理人规则（3A）

MVP 只有一个全局 `委托诉讼代理人` 区块，不支持按主体区分代理状态。

| 输入情况 | 业务输出 | 状态/处理 |
| --- | --- | --- |
| 所有当事人均无代理人 | `是否委托 = 无`，`代理人 = null` | 正常 |
| 至少一个当事人有代理人 | `是否委托 = 有`，`代理人` 输出实际代理人 | 正常 |
| 代理状态无法判断 | `是否委托 = null`，`代理人 = null` | `needs_review` |
| 多当事人且部分有、部分无 | `是否委托 = 有`，保留代理人列表 | `needs_review`，warning：MVP 不支持按主体区分代理状态 |
| `是否委托 = 有` 但 `代理人 = null` | 保留 | `needs_review` |
| `是否委托 = 无` 但 `代理人` 非空 | Schema 会拒绝 | `error`（结构错误） |

## 4. 枚举组合规则（5B）

Schema 保持多选/现状；以下规则由业务校验执行。

### 4.1 `orgType`

当前 15 个选项分为“法律形式”和“上市状态”：

- 法律形式：有限责任公司、股份有限公司、其他企业法人、事业单位、社会团体、基金会、社会服务机构、机关法人、农村集体经济组织法人、城镇农村的合作经济组织法人、基层群众性自治组织法人、个人独资企业、合伙企业、不具有法人资格的专业服务机构；
- 上市状态：上市公司。

规则：

1. 最多一个法律形式；
2. `上市公司` 只能与 `股份有限公司` 同时出现；
3. `上市公司` 单独出现 → warning；
4. `上市公司` 与 `股份有限公司` 之外的法律形式同时出现 → warning；
5. `其他企业法人` 与具体法律形式同时出现 → warning；
6. 违反以上任一条 → `needs_review`，保留原数组，不自动改写。

### 4.2 `stateOwnershipType`

- 最多一个；
- `控股` + `参股` 同时出现 → `needs_review`；
- 非空时 `ownership` 必须为 `国有`（Schema 已有单向约束；业务层再检查一次）。

### 4.3 `repaymentMethod`

- 单笔借款最多一个；
- 多个同时出现 → `needs_review`；
- `其他` 与其他选项同时出现 → `needs_review`；
- `方式` 含 `其他` 但 `其他说明` 为 null → warning（允许，提示说明缺失）。

### 4.4 `registrationType`

- 单个担保物最多一个；
- `正式登记` + `预告登记` 同时出现 → `needs_review`；
- 无担保/未办理登记时非空 → warning/`needs_review`。

### 4.5 不拦截的多选

- `acceleration`：允许“提前还款”和“解除合同”同时选；
- `deliveryMethod`：允许多种交付方式；
- `orgType` 的数组本身仍是数组，但按 4.1 做组合校验。

### 4.6 借款利率的补充口径（逾期利率）

模板没有独立的“逾期利率”字段；Stage 0 在 `事实与理由/5.借款利率` 下新增 `补充内容` 文本字段，专门保存利率补充说明。

- `利率` 填百分数数值，`周期` 填年/季/月；
- `补充内容` 保存借期内不计息、逾期利率标准、利率调整方式等原文/归纳；
- 如果文本只约定逾期利率（例如“借期内不计利息，逾期按年利率 4%”），建议 `利率=4`、`周期=年`，`补充内容` 写“借期内不计利息，逾期按尚欠本金年利率4%支付逾期利息”；
- 不要把逾期利率解释成借期内利率；prompt 中要明确 `补充内容` 的语义；
- `合同条款编号` 仍只放条款号，不拿它承载利率文本；
- `补充内容` 未提及时为 null，不要用借期内/逾期推断填空。

## 5. 金额规则

只在相关字段都非空时检查；缺失不自动补 0。

| 规则 | 处理 |
| --- | --- |
| `尚欠本金 + 尚欠利息 = 标的总额` | 不相等 → `needs_review`，保留原值 |
| `计算基数 = 尚欠本金`（两者都填） | 不相等 → `needs_review` |
| `尚欠本金 <= 实际提供 - 已还本金`（三者都填） | 超出 → `needs_review` |
| `实际提供 <= 约定`（两者都填） | 超出 → warning，不强制 |
| 金额出现负数、非两位小数 | Schema 已拒绝 → `error` |

不要为了通过校验而修改金额、取较大值或补齐缺失值。

## 6. 日期规则

只在相关日期都非空时检查；不完整日期保持 null，原文放 `期限原文`/review。

| 规则 | 处理 |
| --- | --- |
| `约定起始日期 <= 约定截止日期` | 违反 → `needs_review` |
| `利息起算日期 <= 暂计截止日期` | 违反 → `needs_review` |
| `提供日期 <= 暂计截止日期`（都填） | 违反 → warning |
| 任何日期不是合法日历日期 | Schema/FormatChecker 拒绝 → `error` |
| 从“2026年3月底前”等不完整日期补出具体日 | 禁止；保留原文，日期 null |
| 用运行当天补签署日期/截止日期/逾期时长 | 禁止 |

日期检查不使用“今天”推断“是否到期”；`是否到期` 必须有明确文本依据。

## 7. 明确否定与未提及

- 只有文本明确出现“没有、无、未、不存在、未签订、未办理”等否定表达，才允许填 `否`/`无`；
- 文本沉默、选项未提及、勾选状态缺失 → `null`；
- `否/无` 的 evidence `quote` 必须包含否定词；否则 `needs_review`；
- 不得从其他字段级联推断“否”。例如：
  - 没提到担保 ≠ 没有担保；
  - 没提到委托代理人 ≠ 没有委托代理人；
  - 没提到管辖约定 ≠ 没有管辖约定。

## 8. 证据规则（E2）

### 8.1 必须有证据的关键字段

- 当事人：`name`、`sex`、`certificateType`、`certificateNumber`、`creditCode`、`role`、主体索引；
- 代理人：`是否委托`、`name`、`authorization`；
- 诉讼请求：本金、利息、起算日期、截止日期、标的总额、费用主张；
- 事实与理由：借款金额、借款期限、利率、提供时间、还款情况、逾期、担保各是否项；
- 所有 `是/否/有/无` 枚举；
- 所有金额和日期。

长文本字段（诉讼请求原文、事实与理由原文、其他说明）允许整段引用，不要求逐句定位。

### 8.2 证据结构

每条 evidence 至少包含：

```json
{
  "fieldPath": "/原告/0/data/name",
  "subjectId": "P1",
  "fileContextIndex": 0,
  "charStart": 12,
  "charEnd": 20,
  "quote": "南通紫星广告装饰工程有限公司",
  "kind": "explicit",
  "confidence": 0.98
}
```

- `quote` 必须等于 `fileContext[fileContextIndex]` 中 `[charStart:charEnd)` 的文本；
- `charEnd > charStart`；
- `kind`：`explicit`（明示）、`negative`（明确否定）、`derived`（由文本结构推导，需谨慎）；
- 关键字段无 evidence → `needs_review`；
- evidence 与字段值不一致 → `needs_review`/`conflict`。

## 9. 费用边界（第 5/6 项）

- 第 5 项 `是否主张实现债权的费用`：律师费、保全费、公证费、执行费等；
- 第 6 项 `是否主张诉讼费用`：诉讼费用；
- 两者可以同时为 `是`；
- 第 5 项 `明细` 中出现“诉讼费用” → warning，提示口径重叠；
- 不把第 6 项自动复制到第 5 项，也不把第 5 项自动复制到第 6 项。

## 10. 担保条件规则

| 条件 | 要求 |
| --- | --- |
| `10.是否签订物的担保合同 = 否` | `11.担保人、担保物` 必须为 null |
| `12.是否最高额担保 = 否` | `担保债权的确定时间`、`担保额度` 必须为 null |
| `13.是否办理抵押、质押登记 = 否` | `登记类型` 必须为 null |
| `14.是否签订保证合同 = 否` | `签订时间`、`保证人`、`主要内容`、`保证方式` 必须为 null |
| `15.其他担保方式 = 否` | `形式`、`签订时间` 必须为 null |
| `10 = 否` 但 `12/13/14/15` 有肯定值 | `needs_review`（跨项矛盾） |

Schema 已覆盖 9/10/12/13/14/15 的部分条件；`10=否 → 11=null` 和跨项矛盾由业务校验补足。

## 11. 冲突处理

- 同一字段出现多个候选值 → 字段置 null，写入 `conflicts`；
- 不按“金额更大”“日期更近”“句子更靠后”自行选择；
- 冲突记录必须包含 `fieldPath`、`subjectId`、候选值、来源 evidence；
- 冲突存在 → `status = needs_review`；
- 下游只能把 `ok` 当最终结果；`needs_review` 必须人工确认。

## 12. 业务校验输出

业务校验结果进入 `review`：

- `warnings`：不阻断但需关注；
- `conflicts`：候选值冲突；
- `missing`：关键字段缺失/关键证据缺失；
- `subjectIndex`：主体索引；
- `evidence`：关键字段证据。

`status=error` 时，`data` 为 null；`review` 可以为空数组或包含已生成的主体索引/证据。
